# 投资命题与多证据验证系统：AI 辅助开发规范与全局架构约束 (AGENTS.md)

> 本文件是 **FinHypothesis-Verifier** 的架构规范、工程守则与 Agent 执行协议。所有参与本项目的 AI Agent 与研发人员，在探索、编码、测试、部署与文档维护前，应先阅读本文件及已确认实施方案。
>
> 版本：v1.1（2026-10-30）。依据《投资命题与多证据验证系统实施方案 v6.1 全链路闭环与去硬编码修订版》制定；沿用其中明确继承的数据能力、接口及累计/单季口径规则。目标是在当前交付窗口内完成真实、可操作、可追溯的 Web MVP。

## 🏛️ 零、事实来源与决策基准

遇到接口参数、字段、研究边界、状态与架构取舍时，依次核验：

1. **用户当前明确指令与确认决策**：用户后续明确调整优先于本文件与旧方案。
2. **已确认方案**：v6.1 为业务规则主版本；冲突处以 v6.1 为准。示例数字与判定不属于运行事实。
3. **当前可复现接口事实**：工作区 `script/` 中的接口探针、当前工具 Schema、真实请求与返回记录。方案所称“已验证”仍须区分历史验证和本次运行证据。
4. **当前代码与测试事实**：检查实现是否偏离设计，或文档是否滞后，不机械以任一方覆盖另一方。

- 接口文档与真实返回冲突时，保留请求、响应及差异，按实测修正适配器和映射；不得伪造字段或参数让测试通过。
- 常规字段映射、路径修正、补齐请求模型与局部错误处理，可在既定范围内直接处理并记录。只有影响产品目标、数据权限、费用或核心契约的实质变更才需要用户决策。
- 本规范用于收敛执行，不启动新一轮方案重构，也不将可选优化变成必做任务。

## 🛠️ 一、架构核心：交互展示 + 状态编排与质检 + 真实工具

本项目定位为**单命题、单公司验证工作台**，先打通中际旭创（300308.SZ）典型案例。其他命题按实际能力处理，不承诺通用投研平台能力。

| 层级 | 目录 | 职责 |
| :--- | :--- | :--- |
| 交互与 HTTP 入口 | `fin_verifier/web/`、`fin_verifier/main.py` | 输入、确认、状态展示、证据穿透、历史任务、比较与追问；请求校验与业务调用 |
| 编排与状态质检 | `fin_verifier/core/`、`fin_verifier/prompts/` | 领域契约、任务状态、证据组织、两阶段质检、报告与追问 |
| 工具与数据接入 | `fin_verifier/tools/` | 扶摇、iFinD、LLM 适配、单位解析、确定性计算、超时与重试 |

### 1. 层间职责与范围约束
- 前端不直接持有供应商密钥、不直接请求供应商、不另写财务计算或结论判定逻辑。
- 工具层负责协议、请求、解析与结构化错误，不自行决定主命题成立与否；客户端不相互调用构成隐式业务流程。
- 编排层根据本次子问题声明必需与可选数据，统一处理降级、补检和状态流转。
- LLM 负责澄清、拆解、受证据约束的解释与生成；Python 负责财务计算、引用检查、单位与期间校验。
- 采用单 Agent 阶段流水线；不引入多 Agent 协商、向量数据库、长期记忆、通用调度平台或额外框架。
- 先完成真实主链路，再完成既定交互；不新增演示案例、研究维度或产品功能来追求“创新感”。
- **标的中立与去硬编码铁律**：核心流水线（`pipeline.py`）、提示词（`prompts/*.py`）、适配器与验证器必须 100% 保持标的中立，严禁写死任何特定个股名称、专有产品词或硬编码检索关键词；检索词必须源自 Step 1 拆解计划；严禁在 Pydantic 数据模型默认值或验证器中注入特定个股的反转条件或合规兜底文本。
- **严禁跳过 Step 0 命题澄清**：任何命题必须走完 Step 0 澄清润色、标的消歧、起止日期校验与用户编辑确认流程；严禁在前端或后端提供绕过澄清直接启动验证流水线的偷步入口；后端 `/api/verify` 必须强校验标的确认状态与时间合理性。

### 2. 主链路顺序
1. Step 0：输入、标的消歧、合规引导、命题澄清与用户编辑确认。
2. Step 1：从四大能力维度选择与命题相关的维度，生成 2–4 个尽量减少重叠的子假设及检索计划。
3. Step 2：按计划获取真实数据，保存原始响应。
4. Step 3：抽取并核验事实，完成确定性计算；无效事实不得继续流转。
5. Step 4：检查证据覆盖，最多进行一轮定向补检；新增材料重新经过抽取、核验与计算。
6. Step 5：按具体子假设组织支持、反对与无法验证项。
7. Step 6：合成前质检 → 报告合成 → 合成后质检 → 成功、降级成功或失败落盘。
8. Step 7：展示、保存、比较与基于已存证据的追问。

架构图、日志和代码必须遵守以上顺序，不能把合成后质检放到合成前执行。

## 📜 二、领域模型、数据与接口契约

### 1. 单一模型来源与强 ID 闭环
- 以 `fin_verifier/core/models.py` 为唯一领域契约来源；前端、接口和提示词围绕同一套字段工作。
- “不可变 Schema”指契约稳定，不要求把运行中的任务对象全部设为不可修改。任务状态按状态机更新。
- 阶段尚未产生的字段可使用明确的待生成状态或空值，不得提前填入结论、置信度、最新报告期等虚假占位值。
- 闭环必须真实落盘：`raw_ref_id → fact_id → computation_id → evidence_id → sub_id → report`。纯定性证据可以直接引用原始材料与事实，无须强造计算节点。
- `ResearchTask` 持久化 `raw_records`、`extracted_facts`、`computed_metrics`、子假设、证据、报告与追问；服务重启后仍可回溯。
- `inherited_source_ids` 只存 `raw_ref_id`；`fact_ids` 只存 `fact_id`；计算项通过 `input_fact_ids` 关联输入；报告引用真实存在的证据 ID。
- 封闭值使用 Enum 或 Literal 约束，包括证据极性、结论状态、置信度与反转类型；代码、Prompt 与前端不得自行发明别名。
- 同一任务内 ID 唯一，证据只能引用该任务的有效材料；结论状态与置信度分字段。

### 2. 标的、时间、单位与统计口径
- 标的统一为标准 `thscode` 与公司名称；多候选返回选择信息，由用户确认，不静默挑选第一项。
- 用户编辑确认后，后端重新校验标的、日期与合规边界；不能直接信任澄清阶段之前的值。
- 请求采用结构化起止日期，消除 `period_range` 自由文本的解析歧义；澄清与验证接口共用同一时间模型。
- 区分分析期、信息截至时间 `data_cutoff_time`、最新已披露财务期 `latest_financial_period` 与实际取数期 `retrieved_periods`。
- 同比基期可在分析期外，必须单独标记；后续新报告单列观察，不混入目标期归因。披露检索窗口不得越过信息截至时间。
- 供应商响应保留原始金额、单位、报告期、请求参数和获取时间。计算金额统一归一为亿元，保留数值精度；展示时再格式化。
- **物理接口结构约束**：
  - 扶摇财务三表采用整型 `fiscal_year` 与字符串 `fiscal_period`（'Q1'~'Q4'，Q4 即年报 FY）标识期间，并无 `report_date`；单季拆解须严格按同年相邻累计期做减法，不得依赖不存在的日期字段。
  - 扶摇指标接口返回 `data.abilities[*].indicators[*].{index_id, value}`，无 `name` 字段；指标名称由映射表解析，严禁读取 `item.get('name')` 产生空指标。
  - iFinD 返回的多行 Markdown 时序表必须按报告期逐行解析为多条记录（`list[dict]`），严禁单 dict 循环赋值覆盖历史数据。
- 百分比、百分点、金额、销量与估值倍数分别处理；单位不明时记录缺口，不猜测倍数。
- 利润表和现金流量表累计值按 YTD 处理，资产负债表按时点余额处理。单季拆解仅适用于可拆的累计流量，同年相邻累计期相减；Q1 直接取累计值。
- 同比须报告期后缀相同且年份差 1，并确保指标、主体、合并范围与累计/单季口径一致；ROE、比率等不得直接用累计值相减伪造单季指标。
- 基期缺失、为零或负数时明确计算定义与限制，不能把亏损收窄简单描述为常规正基期增长。
- 个股与指数比较使用相同日期边界和一致收益率算法，注明复权口径；不把股价相对表现当作经营归因的直接证明。

### 3. HTTP 接口与异步行为
实施方案表格实际列出 **9 个接口**，以表格为准，不为凑“7 个”删除接口：

| 方法 | 路径 | 职责 |
| :--- | :--- | :--- |
| GET | `/api/demos` | 载入命题模板，不返回硬编码研究答案 |
| GET | `/api/tickers/search` | 标的查询与消歧候选 |
| POST | `/api/clarify` | 返回可编辑命题、标的、日期与合规说明 |
| POST | `/api/verify` | 创建任务并异步启动流水线 |
| GET | `/api/tasks/{task_id}` | 状态、日志及已生成任务内容 |
| GET | `/api/tasks` | 历史任务与收藏筛选 |
| PATCH | `/api/tasks/{task_id}/star` | 明确设置收藏与标签，不重复追加同一标签 |
| GET | `/api/compare` | 基于已存任务并排比较，不新增 LLM 调用 |
| POST | `/api/tasks/{task_id}/inquire` | 基于已存证据回答并保存追问 |

- 编码前补齐请求与响应模型、空值、错误码和状态码；不为此另造复杂协议框架。
- `/api/verify` 在成功创建任务后尽快返回 `task_id`，不能等待整条研究完成；“10ms”不是硬性承诺。
- 同步 HTTP/SDK 调用不得堵塞异步事件循环。采用与当前栈匹配的线程执行或异步方式，不新增重型任务队列。
- 未知任务返回明确的未找到错误；未完成或失败任务不伪装成可正常比较、追问的报告。
- 追问同样受引用、事实与合规检查约束；材料不足时明确回答无法据此验证，不调用模型记忆补充金融事实。

## ⚙️ 三、证据核验、研究判断与失败降级铁律

### 1. 真实来源与原文防伪
- 生产运行只能使用真实数据；不得用示例、测试夹具或模型生成文本兜底冒充上游返回。
- 原始响应先保存，再抽取。引文核验只规范空白与换行，保留小数点、负号、百分号及其他标点；空引文不能作为核验成功。
- 引文必须存在于指定 `raw_ref_id` 的真实原文中；进一步核对数值、单位、指标归属与报告期，不能只检查数字出现过。
- 结构化财务字段由代码直接读取，记录字段路径或等效定位及原值，无须让模型重新抄录并生成“公告原话”。
- **抽取范围严禁盲目截断**：严禁设置无依据的材料数量上限（如 `if len(...) >= 4: break`）。所有检索到的三表、公告、新闻、iFinD 表格及行业指数均须进入抽取池；三表指标由 Python 直接抽取为结构化事实（归一为亿元），文本公告与新闻由 LLM 结构化抽取。
- `verified_in_raw` 由程序核验设置，不接受 LLM 自报成功。
- 区分法定公告、结构化财报、iFinD 汇总表、新闻摘要与衍生计算。来源标注由实际返回材料决定，不仅凭工具名判断；未经审计的披露不得称为已审计事实。
- 查询未命中、摘要截断、接口失败，只能说明当前检索无法取得，不能据此断言该事实不存在或所有公开材料均未披露。

### 2. 审慎归因、证据分类与结论边界
- 四大能力池是拆解依据，不要求每个命题强制覆盖全部四维；研究上重要但能力不足的内容保留缺口。
- 每条支持或反对证据绑定具体子假设，说明支持或削弱的具体判断。风险提示、背景信息不能自动成为反证。
- 三角编组用于呈现推理链；原始数字与其计算比率继承同一来源，不重复增加独立来源数量或置信度。
- 收入增长、提价事实、渠道变化与销量差异，不能单独证明对利润增量的主要贡献；缺少贡献拆分时限制结论强度。
- H3 等复合检查项分别记录结果，不允许“一项成立、整组成立”。主结论不能按证据条数投票或对支持度做无依据的平均。
- 中际旭创 Demo 只固定输入与执行路径；所有数字、立场、置信度和原因解释来自本次有效证据，不硬编码示例答案。
- 事实、确定性计算、逻辑推断与不确定信息明确区分；未经验证的因果解释不得塞入事实摘要。
- 反转条件区分历史归因与未来持续性；注明依据，无依据不生成数值阈值。未来单项指标变化不自动推翻历史事实，也不自动宣布模式失效。

### 3. 确定性计算与两阶段门禁
- 财务数值由 Python 计算；LLM 可提出受约束的计算计划，不能自行输出数字并充作已执行计算。
- AST 求值仅允许白名单数字、变量和运算，不使用裸 `eval`，不开放属性访问、函数调用、导入或任意代码执行。
- 校验输入变量、除零、非有限结果、表达式长度及运算规模；数学可执行不等于单位或口径正确。
- 每项计算保存公式、输入事实 ID、代入过程、结果、单位和口径；核验失败的计算不得进入有效证据。
- **合成前门禁**检查原文、事实、计算和 ID 链；**合成后门禁**检查报告结构、引用、反转条件、缺口保留与合规输出。
- **门禁硬拦截与严禁洗白后门**：门禁必须真实拦截不合规内容。严禁在进入验证前静默剪裁非法 ID、截断非法列表，或自动用有效 ID 填充冒充通过；严禁在 Pydantic 校验器中静默补全伪造的反转条件或免责声明。门禁质检不通过时，必须直接抛出异常、记录缺口进入降级状态（`PARTIALLY_COMPLETED`）或标记失败（`FAILED`）。
- 代码检查结构和确定性规则；LLM 陈述证据关系及因果解释。不得宣称正则或合法 JSON 已证明推理正确。
- 合规检查覆盖澄清、报告与追问；避免把“本产品不提供买卖建议”等边界说明误判为违规推荐。

### 4. 重试、补检、终态与错误透传
- 外部调用显式设置超时；重试次数及退避参数集中配置。“3 次”统一指最多 3 次总尝试（含首次），不叠加客户端与流水线重试放大调用。
- 限流、暂时网络错误等才重试；鉴权失败、非法参数、Schema 不兼容等按原因处理，不能无差别重复调用。
- 定向补检最多一轮；与单次接口重试分开计数。补检数据重新核验，不无限扩展查询范围。
- **状态流转闭环与子假设判定更新**：定向补检获取新数据后，任务状态必须先切回 `EXTRACTING_AND_COMPUTING` 重新流转抽取与计算，严禁跳步；Step 5 证据分类必须依据归属证据状态真实回写并更新对应子假设的结论判定（`verdict_status`）、置信度（`confidence_level`）与证据缺口（`evidence_gap_note`），严禁所有子假设终身滞留为 `UNVERIFIABLE/LOW`。
- `COMPLETED`：有效报告通过全部门禁，无影响本次必要验证的客观缺口。
- `PARTIALLY_COMPLETED`：有效报告通过门禁，但存在明确的数据或验证缺口；报告保留缺口和推断限制。
- `FAILED`：无法产出通过门禁的有效报告。无效、伪造或违规内容不对用户展示；内部记录失败原因供排障。
- 局部抽取失败可以丢弃该项并保留缺口；不得为了避免失败而把无效材料改成“正常证据”。
- 空结果、缺失、零值、解析错误与调用失败分别记录。保留可诊断信息，日志和前端错误均不得泄露密钥。

## 🛑 四、通用工程纪律与开发约束

### 1. 目录、环境与配置
- 项目根目录为 `同花顺笔试/`；业务源码在 `fin_verifier/`，自动化测试在 `tests/`，交付说明在 `docs/`。
- 既有 `script/` 归档内容保持原样；新增临时探针与样本集中存放，不散落业务目录。`fin_verifier/data/tasks/` 是必要运行数据，不属于应删除的临时产物。
- 使用项目虚拟环境解释器。Windows 使用实际 `.venv/Scripts/python.exe`，其他环境使用对应 `.venv/bin/python`；不擅自改用全局解释器。
- 路径以配置文件或模块位置解析，兼容中文路径与空格，不依赖命令启动时的当前目录。
- 从环境变量或既有 `script/.env` 加载配置；环境变量优先。只交付 `.env.example`，不打印或迁移真实密钥到源码。
- LLM 模型名、API 地址与超时可配置，以当前账号实际可调用结果为准，不为某个名称硬编码特殊分支。

### 2. 最小实现与状态持久化
- 在现有技术栈与方案目录内完成任务；稳定契约的实质变更说明原因并同步调用方，不堆叠旧字段兼容补丁。
- 任务使用同目录临时文件写入后 `os.replace` 原子替换；原子替换不等于并发安全，同一任务的流水线、收藏和追问写入须串行或加锁，避免覆盖数据。
- 记录当前节点、重试、补检、阶段耗时及结构化错误。对外响应不暴露供应商鉴权头与敏感请求信息。
- 服务重启可读取已保存报告；中途任务不能永久伪装为运行中，应标记中断。MVP 不要求自动恢复执行或另建调度系统。
- 模型输出经 Pydantic 校验；解析或修复尝试有上限，不允许无限循环直到“成功”。

### 3. 安全与前端呈现
- `.gitignore` 排除 `.env`、密钥、虚拟环境、日志、运行任务原始数据与临时缓存。发布前检查暂存内容及已跟踪文件，仅新增忽略规则不能移除已提交秘密。
- 不在公开仓库提交受限数据；测试夹具最小化、脱敏并符合来源使用权限。
- task ID 与存储路径由程序校验，禁止通过请求参数越界读写任意文件。
- 上游公告、新闻和 LLM 文本视为不可信内容；前端按文本或经过安全转义的内容渲染，不直接插入任意 HTML。
- 页面显示真实运行状态与可理解的错误；不展示伪进度、预设结论或未生成的证据卡片。
- 公网验收包含外部设备实际操作和评审期间保活；不以隧道命令启动成功代替 Web 产品可用。

## 🧭 五、AI Agent 执行、验收与交付流程

### 1. 执行顺序与协作纪律
- 默认由单一执行 Agent 完成编码、测试与交付，用户作为产品 Owner 审查关键决策；本文件不要求另启多 Agent。
- 先核对环境和已有探针，固化最小模型及接口，再实现工具层、流水线、真实端到端、前端与交付。
- 按阶段简短汇报实际完成、验证证据、阻塞及下一步；常规实现自主推进，不因低风险细节反复等待确认。
- 不反复重写已封版方案；只有真实取数或实现证据暴露的阻塞问题才调整相应部分。

### 2. 测试与代码走查
- 检查关键路径实现与方案一致后运行测试；失败则按证据修复，不把“逐行阅读”变成拖延所有运行验证的形式门槛。
- 必测：原文篡改、无效引用、单位与期间、同比基期、计算异常、补检上限、供应商超时/限流、缺失降级、非法 LLM 输出、合规输入与输出、任务保存后重读。
- 测试允许 mock 网络错误和构造边界夹具；生产路径不得引用这些数据兜底。真实集成测试与离线测试分开标记，不把离线通过宣称为真实接口通过。
- 真实端到端跑通中际旭创案例，人工抽查关键数字、原文与算式；验证澄清编辑、状态推进、证据抽屉、追问、收藏与对比。
- 模型 JSON 合法或供应商调用一次成功，不等于全链路正确；验收记录以实际执行结果为准。

### 3. 完成证据分级
- `reported`：仅有描述、历史结果或未经当前环境复核的日志。
- `implemented`：代码、配置或文档已实际落地，尚不能据此宣称运行通过。
- `verified`：在当前工程环境执行相关检查，取得可定位、可复现的结果。
- 实际记录 AI 工具、参与环节、人工修正与验证过程；不得预先编造测试通过、部署成功或用户验证记录。

### 4. 最终交付清单
- 可实际操作的 Web URL，外部访问已验证，并明确服务与隧道保活方式。
- 源代码仓库及可发现的 README，说明启动命令、环境变量、用户、设计、AI 角色、数据来源、边界和未做事项；README 在 `docs/` 时根目录提供入口。
- `docs/AI_USAGE_RECORD.md` 与 `docs/TEST_REPORT.md`，如实记录通过、失败、未验证及已知限制。
- 实际录制并提交 60–180 秒演示视频；脚本不能替代视频。若真实运行较长，可剪辑并注明等待过程，不伪装处理速度。
- 交付前检查密钥与受限数据未公开、核心结论可回溯、缺口可见、无效内容未展示。完成时间以用户实际题面和当前指令为准，不照搬旧方案剩余时长。

本规范约束既定范围内的实施与验收，不要求新增功能、研究模型或基础设施。
